# 方案一：参考图驱动的具体视觉重构
## 目标与设计优先级
面向班主任的 Operate 工作台：快速处理今日班务，同时保留参考图的温暖校园感。C1首页、C2听写、C3学生、C4作业、C5手机首页、C6手机批改是直接视觉依据。
优先级：用户最新要求与数据真实性 > 本轮明确构图要求 > 已批准页面 > 旧通用UI偏好。旧规则“表格为主要信息面”“不能有彩色面板”不能用来抹掉参考图；有用途的任务分区、浅色底和插画容器可以保留。禁止无意义嵌套边框仍有效。不能为了丰富而造数据、加无效入口或把每页换成同一张大横幅。

## 当前代码确认与启动任务 V0（计入V1准备，不另设人工门槛）
1. 读当前导航、状态、基线、账本；核对 Git HEAD 与本包基线的差异。检查 .codegraph 是否存在再决定定位方式。
2. 打开本门原图，采集实际页；检查 ThemeArtwork → Artwork → picture/img 的真实 DOM 和计算样式。
3. 路由级 ClassroomPages.module.css 存在通用 campus-art 规则；DashboardView.module.css 又声明图片铺满。以浏览器计算样式查清胜出的 width/height/object-fit 规则，记录文件/选择器，禁止只凭猜测删除。
4. Artwork.tsx 存在内联 objectFit/objectPosition，CSS object-fit 未必能覆盖；definitions.ts 控制 fit、焦点和移动资源。必须一并检查，不能仅增加 !important。
5. 修共享根因时先恢复页面拥有图片尺寸和裁切权；通用层只保留真正通用能力。不得一口气整理上万行CSS或恢复已退出的旧CSS生成链。
6. 先确认首屏母版与手机重排，再推广到后续门槛。

## V1 的具体实施顺序
A. 壳层：检查 shell.module.css 和 WorkbenchShell.tsx；保留19模块四组导航、账号与真实保存状态。调整主内容宽度、标题层级和图标尺度，侧栏插画只能在不挤压导航时展示。
B. 桌面首页：DashboardView.tsx/CSS。上层为“今日待办＋教室场景”，场景约占该区域右侧45%–50%，铺满自身区域，主体可辨认。此范围是本方案目标而非原图测量事实。中层课程左、听写右；下层班务与学生提醒组织成较平缓的条目区域，避免四个等重白盒。保留真实数据内容，不能照抄参考中的日期、学生和统计。
C. 视觉语言：沿用 definitions.ts 的暖白、浅蓝、浅绿、暖黄和青蓝主色；大色块用于任务区分，红色用于异常。桌面页标题建议32–40px、模块标题20–24px、正文15–17px；手机页标题24–28px、正文至少14–16px。这些是初始设计区间，实际以阅读、真实参考对比和人工结果为准。
D. 图像：优先修复已有 home.scene、dictation.context 的容器和焦点，复用 public/art/campus；缺图直接记录，未经评估不重新生成整套资产。手机用已有 mobileSrc，禁止缩小桌面布局冒充手机设计。
E. 手机首页：日期/校园横幅、待办、今日课程、常用入口依次呈现；首屏能看见主要任务和操作。既有提醒放后面。保留底栏与返回语义，避开安全区域，按钮至少44px触达区域。
F. 验证：先桌面1536×1024、手机390×844一次批量检查，集中修复，再确认一次。仍有问题则记录 needs-fix 和具体阻碍，不无限微调，也不假报通过。
G. V1提交证据并暂停；用户认可才允许推广母版。

## 后续实施方法
按02逐页卡执行，每页独立提交或明确可审查的提交组；已有controller/read-model/operations保留。低频页面若仍在ClassroomApp.tsx，可为局部样式隔离抽取纯视图，但不能重新实现写入逻辑。
提取公用部分仅限已出现的稳定重复：页头、状态标签、任务上下文、详情时间线；首页、名册、作业、批改、课表、座位的主体构图分别保留。
共享改动使既有视觉批准需要复核；重新审核范围按VISUAL_BASELINE执行。绝不把“共享优化”当作绕过人工门槛的理由。

## 执行前须修补的检查器缺口（V0工程任务）
当前qa:visual-baseline仅辅助验收，并非不可绕过权限系统：
- sharedRegressionTriggers 的文件路径匹配需覆盖 theme.ts/primitives.tsx 等实际文件，现有无扩展名触发项可能漏检。
- Git diff HEAD只发现未提交变化；补充与上次批准commit比较，提交后仍须检测共享变化。
- user-approved页面须反向绑定其门槛的真实批准；重复证据路径、路径穿越、只填两个文件不区分桌面手机均应拒绝。
- ready-for-review须关联当前产品提交、viewport、截图哈希、实际URL/状态；监工PASS与用户批准独立记录。
- 审核器必须能表示needs-fix门槛，或明确映射到active+页面needs-fix，避免文档与枚举冲突。
为这些真实负例写针对性测试。失败时修检查器，不降低阈值。此处是待实施任务，当前资料交付没有声称已修复。
